# Git 협업 규약

A/B/C는 서로 다른 머신의 에이전트이며 GitHub로 상태를 공유한다. **발견한 에이전트가 기록하고, 담당 에이전트가 고치고, 사람은 방향과 정책을 정한다.** 상시 감시는 없고 세션을 시작할 때 확인한다. 리뷰 요청은 에이전트를 깨우지 않으므로 담당의 다음 세션에 처리된다.

## 매 세션

```text
git status -sb
git fetch origin
gh pr status
gh pr list --search "review-requested:@me" --state open
```

1. 새 활동이 있는 PR만 `gh pr view <번호> --comments`로 읽는다. 코드 줄 댓글은 `gh api "repos/{owner}/{repo}/pulls/<번호>/comments"`로 본다. 이미 본 SHA 이후의 변경만 읽는다.
2. 받은 리뷰 요청과 다른 역할을 막는 자기 수정을 자기 작업보다 먼저 처리한다. 모든 응답을 기다리느라 독립 작업을 멈추지 않는다.
3. 작업은 `origin/main`에서 분기한 `commerce/a|b|c/<작업명>` 브랜치에서 한다. 자기 clone을 쓰고, 병렬 작업은 worktree로 나눈다. 명시한 경로만 stage하고 작은 단위로 커밋해 Draft PR로 올린다. PR base는 `main`이다.
4. 리뷰를 받을 준비가 되면 `gh pr ready <번호>`로 바꾸고 아래 표의 검토자에게 요청한다. PR 본문의 `다음 행동 / 담당 계정` 한 줄을 최신으로 둔다.

원격에 접근할 수 없으면 미확인이라고 적고 독립 작업을 계속한다.

## 누가 검토하나

누가 검토하는지는 이 표에만 적는다.

| 변경 | 필요한 것 |
| --- | --- |
| 자기 역할 내부. 다른 역할이 쓰는 동작·계약이 바뀌지 않음 | 관련 검사 + CI |
| 다른 역할이 쓰는 동작·계약·실행 환경. requirements·lock 포함 | 위 + 영향받는 역할의 검토. lock은 C가 호환을 확인한다 |
| 원자료(Dunnhumby·Instacart)를 흉내 낸 합성 데이터의 생성기를 새로 만들거나 규칙을 바꿈, 그런 데이터를 손으로 쓴 파일, 원자료 집계 보고서 | 위 + C가 PR diff에 원자료 값·실제 ID가 없는지 확인([데이터](../design/data.md) §6) |
| 설계·팀 문서 | 위 + 그 문서를 따르는 다른 역할 한 명. `docs/design/` 아래 새 문서는 그 결론의 영향을 받는 다른 역할 |
| 계약·모델 방향·보안 원칙·소유권·검사 정책의 미확정 변경 | 위 + 사람의 결정 기록([결정 요약](../design/decisions.md)) |

- 합성 데이터 확인은 생성기에 한 번 한다. 확인된 생성기로 seed·개수만 바꾼 결과물과 원자료와 무관한 합성 값(A의 판매자·상품·주문 seed 등)은 내부 변경이다.
- [열린 항목](../design/open-questions.md)의 '이미 열린 구현 선택'(인코더 ID·예산 등)은 담당이 정하고 PR에 근거를 남긴다. 사소한 구현 선택과 합의된 계약으로 되돌리는 버그 수정도 담당이 처리한다.
- `.github/CODEOWNERS` 경로는 GitHub이 작성자가 아닌 소유자 한 명의 승인을 강제한다. 소비자 영향이 없으면 먼저 보는 사람이 승인한다. 이때 게이트 통과 조건이 느슨해지지 않았는지, lock이면 자기 OS에서 다시 설치해 게이트가 통과하는지 확인한다.
- 자기 검사는 리뷰가 아니다. 같은 계정으로 자기 PR을 승인하지 않고, 한 계정은 한 역할만 맡는다.
- 검토할 역할의 카드 2행에 계정이 아직 없으면 그 PR은 병합하지 않고 기다린다. 기다리는 동안 독립 작업을 계속한다.

역할 사이에서 확인할 것:
- A ↔ B: 주문 이벤트·상품 전달·추천 호출과 응답, 평가 지표의 입력 형식
- B ↔ C: 모델 manifest·학습·가중치 전달·설치
- A ↔ C: 기동·환경변수·수명주기
- 공통 JSON 계약과 실행 환경: C가 조정하고 소비자가 검토

## 리뷰와 문제 전달

- 검토자는 자기 역할이 쓰는 계약과 동작을 확인하고, 확인한 SHA를 리뷰에 적는다. 전체 구현을 다시 이해하거나 대신 쓰지 않는다.
- 버그·계약 위반·통합 실패는 `Request changes`로 남긴다. 남아 있는 동안 병합하지 않는다. 취향이나 완료 조건 밖의 개선은 Comment로 남기며 병합을 막지 않는다. 사람의 결정이 필요하면 선택지·추천안·영향을 적고 그 부분만 보류한다.
- 병합된 코드의 문제나 별도 작업은 담당 계정에 할당한 이슈로 남긴다: 재현 / 기대·실제 동작 / 위반한 계약 / 막힌 작업.
- 고친 사람은 원래 검토자에게 다시 요청한다. push만으로 요청되었다고 보지 않는다. 지적을 일방적으로 해결 처리하지 않는다.
- 담당이 없다고 다른 역할의 구현을 넘겨받지 않는다. 합의된 계약의 stub으로 진행하고 실제 연결 검사가 남았다고 표시한다. 상대에 맞춰 계약이나 stub을 몰래 바꾸지 않는다. 침묵은 승인이 아니다.

## 병합

조건: Ready, 최신 `main` 기준 CI 통과, 위 표의 검토·결정 기록, 남은 `Request changes` 없음. PR 작성자가 조건을 확인한 세션에서 바로 병합한다.

```text
gh pr update-branch <번호>
gh pr merge <번호> --merge
```

- 첫 줄은 브랜치가 뒤처졌을 때만 쓴다. merge 방식이며 `--rebase`는 쓰지 않는다. `main`에서 온 변경만 더한 것은 다시 검토받지 않는다.
- 자동 병합 예약은 쓰지 않는다. 검토 뒤 자기 변경을 더했으면 다시 검토받는다.
- `main` 직접 push, force push, 공개 이력 rebase·amend, 보호 우회, 알 수 없는 변경을 지우는 `reset --hard`·`clean -fd`를 하지 않는다. 다른 담당의 브랜치에 push하지 않는다. 역할 이관은 사람이 정한다.

## 해당할 때만

**의존 PR 쌓기.** 아직 병합되지 않은 PR 위에서 일해야 하면 그 PR 브랜치에서 분기하되 base는 `main`으로 두고 Draft로 연다. 템플릿의 Depends on에 적는다. 의존 PR이 병합되면 `gh pr update-branch`로 `main`을 받아 diff에 자기 변경만 남긴 뒤 Ready로 바꾼다. 의존 PR보다 먼저 병합하지 않는다.

**계약 변경.** schema·함수·반환 타입·오류·모델 버전 변경은 생산자·소비자 영향, fixture, 동작 설명을 함께 올린다. optional 필드 추가도 strict v1에서 자동 호환이 아니다. 기존 경로를 깨면 호환 전환이나 PR 순서를 먼저 정한다. 한 PR에 두 소유자의 변경이 꼭 필요하면 각자 자기 부분을 쓴다. C의 조정은 남의 구현을 대신 고칠 권한이 아니다.

**충돌과 회귀.** 자기 범위의 충돌은 담당이 해결하고 다시 검사한다. 다른 소유자 구현의 충돌은 그 담당에게 넘기고, 어느 동작을 택할지 미정이면 사람에게 올린다. 통합 회귀는 원인 PR·재현·담당을 기록하고 담당이 수정 PR이나 revert PR로 복구한다.

## CI와 저장소 설정

GitHub이 강제하는 것은 두 가지다. 최신 브랜치에서 필수 CI job `scaffold`(모든 게이트와 smoke)가 통과해야 하고, CODEOWNERS 경로는 작성자가 아닌 소유자 한 명이 승인해야 한다. 나머지 검토와 결정은 병합하는 에이전트가 확인한다. 보호 설정이나 CI를 바꾸면 이 절을 같은 PR에서 고친다.

검사가 실패하면 담당이 원인을 고친다. 게이트를 우회하거나 통과 조건을 느슨하게 만들지 않고, 정책을 바꿔야 할 때만 사람이 정한다. 원자료·파생 거래/배정표·DB·가중치·인증 정보·로컬 보관 파일은 올리지 않는다.
