# Git 협업 규약

## 역할과 기본 원칙

A/B/C는 서로 다른 머신의 에이전트이며 GitHub로 작업 상태를 공유한다. **발견한 에이전트가 기록하고, 담당 에이전트가 수정하며, 사람은 방향과 정책을 결정한다.** 상시 감시나 주기 실행은 두지 않고 세션 시작 때 확인한다.

| 변경 종류 | 필요한 확인 | 병합 주체 |
| --- | --- | --- |
| 자기 파트 내부 변경, 외부 동작·계약 영향 없음 | 작성 에이전트의 관련 검사 + CI. CODEOWNERS 경로면 작성자가 아닌 소유자 한 명의 승인도(아래 참고) | 에이전트 또는 GitHub 자동 병합 |
| 다른 파트가 소비하는 동작 변경, 공동 검사·실행 환경 변경 | 관련 검사 + CI + 영향을 받는 다른 역할의 에이전트 검토 | 확인 후 에이전트 또는 자동 병합 |
| 원자료(Dunnhumby·Instacart)를 흉내 낸 합성 데이터의 생성기(스크립트·seed 설정)를 새로 만들거나 생성 규칙을 바꿈, 그런 데이터를 손으로 쓴 파일, 원자료 집계 보고서 | 관련 검사 + CI + C가 PR diff에서 원자료 값·실제 ID가 섞이지 않았는지 확인([데이터](../design/data.md) §6) | 확인 후 에이전트 또는 자동 병합 |
| requirements·lock 변경 | 관련 검사 + CI + C의 호환 검토 | 확인 후 에이전트 또는 자동 병합 |
| 설계·팀 문서 변경 | 그 문서를 따르는 역할의 검토. [모델 비교](../design/comparison.md) 화면 절은 A, [팀 시작 안내](start.md)의 역할 행은 해당 역할, `docs/design/` 아래 새 문서는 그 결론의 영향을 받는 다른 역할(보호 방식 기록은 A·B, NLP 선택 기록은 C). 예외: 자기 카드 2행의 선점 줄과 [계약 문서](../contracts.md)의 자기 게이트 상태 칸은 첫 행(내부 변경)이다 | 확인 후 에이전트 또는 자동 병합 |
| 요구사항·공통 계약·모델 방향(D 결정에 걸린 학습 목표·공유 경계·variant 구성)·보안 원칙·소유권·검사 정책의 미확정 변경. [열린 항목](../design/open-questions.md)의 '이미 열린 구현 선택'(인코더 ID·예산 등)은 담당이 정하고 PR에 근거를 남긴다 | 사람이 선택지와 영향을 보고 결정 + 위의 해당 검증 | 결정 기록 후 에이전트 또는 자동 병합 |

합성 데이터 확인은 생성기에 한 번 한다. PR 본문에 적는 원자료 집계 수치(행 수·해시·비율)는 확인 대상이 아니며, 개별 행이나 ID는 적지 않는다. C가 확인한 생성기로 seed·개수만 바꿔 다시 만든 결과물과, 원자료와 무관한 합성 값(A의 판매자·상품·주문 seed 등)은 내부 변경이다.

CODEOWNERS 승인은 작성자가 아닌 소유자라면 누구의 것이든 GitHub이 인정한다. 소비자 영향이 있으면 영향받는 역할이 검토하고, 그 승인이 GitHub 조건도 함께 채운다. 소비자 영향이 없는 보호 경로 변경(오탈자, 통과 조건을 바꾸지 않는 게이트 정리 등)은 특정 역할을 기다리지 않고 먼저 보는 사람이 승인한다. 이때 확인할 것은 두 가지뿐이다: 게이트 통과 조건이 느슨해지지 않았는지, lock이면 자기 OS에서 재설치한 뒤 게이트가 통과하는지. 결과와 확인한 SHA를 리뷰에 남긴다.

누가 검토하는지는 이 표에만 적는다. 다른 문서에 검토 조건이 보이면 이 표로 옮긴다. 사소한 구현 선택이나 이미 합의된 계약으로 되돌리는 버그 수정은 담당 에이전트가 처리한다. 새 결정이 필요한 경우만 사람에게 올린다. CODEOWNERS 경로라는 이유만으로 모든 수정에 사람의 판단을 요구하지는 않지만, 작성자가 아닌 한 명의 승인은 받아야 한다. GitHub이 이 승인을 강제한다(아래 'CI와 저장소 설정').

각자 본인의 Git 작성자 정보와 GitHub 계정을 사용한다. Git 커밋 이름을 다르게 설정하는 것만으로 별도 리뷰 계정이 되지는 않는다. 작성자의 자체 검사는 동료 리뷰가 아니며 같은 계정으로 자기 PR을 승인하지 않는다. 역할·계정은 각 역할 카드 2행에 기록한다([작업 규칙](working-agreement.md) §1). 도구별 지시 파일은 [AGENTS.md](../../AGENTS.md)를 가리키는 포인터로만 둔다.

## 브랜치와 작업 범위

- `main`: 공동 통합 기준이자 기본 브랜치. PR로만 변경한다.
- `commerce/a/<작업>`, `commerce/b/<작업>`, `commerce/c/<작업>`: 담당별 짧은 작업 브랜치. PR base는 `main`이다.
- `commerce/integration`은 은퇴했다. 여기서 분기하거나 여기로 PR을 보내지 않는다.

각 에이전트는 자기 머신의 clone을 사용한다. 병렬 작업은 별도 worktree/브랜치로 나누며 같은 index나 작업 폴더를 동시에 수정하지 않는다. 담당 범위의 commit/push는 사용자에게 위임받은 범위에서 수행한다. 다른 담당의 브랜치에 임의로 push하거나 구현을 대신 수정하지 않는다. 역할 이관은 사람이 명시적으로 정한다.

## 세션 시작과 진행

1. `git status --short --branch`, `git remote -v`, `gh auth status`로 작업 폴더·기존 변경·계정을 확인한다.
2. `git fetch origin` 후 최근 `main` 변경과 의존 PR을 확인한다. 검토는 해당 head SHA의 diff 또는 별도 review checkout에서 한다.
3. 아래 명령으로 자기 PR의 피드백·실패, 할당된 이슈, 리뷰 요청을 확인한다. 마지막 목록으로 리뷰어가 미지정된 관련 PR도 확인한다. 다른 역할의 카드가 `미선점`이면 역할명과 영향 설명으로 관련 작업을 찾고, 선점이 필요하다고 사용자에게 알린다. 자기 카드가 `미선점`이면 작업 PR보다 선점 PR을 먼저 연다([작업 규칙](working-agreement.md) §1).

```text
gh pr list --author "@me" --state open
gh issue list --assignee "@me" --state open
gh pr list --search "review-requested:@me" --state open
gh pr list --state open --json number,title,author,headRefName,isDraft,reviewRequests
gh pr view <번호> --comments
gh pr view <번호> --json headRefOid,reviews,reviewRequests,autoMergeRequest
gh api --paginate "repos/{owner}/{repo}/pulls/<번호>/comments"
gh pr checks <번호>
```

PR 번호는 실제 번호로 바꾼다. `gh api`의 `{owner}/{repo}`는 현재 저장소에서 해석된다. 본문 댓글뿐 아니라 리뷰 본문과 코드 줄에 달린 댓글도 읽는다. 목록이 잘렸으면 추가 페이지를 확인하고, 상세 조회는 자기 작업과 관련된 PR에 한정한다. 이전에 검토한 PR도 새 수정이 있는지 관련 목록에서 확인한다.

4. 다른 파트를 막는 자기 수정과 받은 리뷰 요청(CODEOWNERS 승인 요청 포함)을 자기 작업보다 먼저 처리한다. 이미 검토한 SHA·미해결 사항을 기준으로 추가 변경만 읽고, 전체 문서를 매번 재요약하지 않는다. 모든 리뷰나 동료 응답을 기다리느라 자기 독립 작업을 멈추지 않는다.
5. 검토 가능한 작은 단위로 구현·검사·커밋하고 명시 경로만 stage한다. 작업 브랜치를 push해 Draft PR로 공유한다. 동작·stub·검사 SHA·재현 명령·영향받는 역할·의존 PR을 기록한다.

검토할 범위의 구현과 자체 검사가 준비되면 `gh pr ready <번호>`로 Draft를 해제하고 소비자에게 리뷰를 요청한다. **Ready는 검토를 시작할 수 있다는 뜻이며 병합 허가가 아니다.** Draft에는 CODEOWNERS의 자동 리뷰 요청이 나가지 않으므로 동료 리뷰 완료까지 Draft 해제를 미루지 않는다. 필수 수정으로 Draft로 돌아간 경우에도 수정·검사 후 같은 순서로 재검토를 요청한다.

원격 접근이 안 되면 미확인 사항을 남기고 독립 작업을 계속한다. 최신 원격 상태를 확인했다고 보고하지 않는다. 리뷰 요청은 에이전트를 깨우지 않으며 담당 에이전트의 다음 세션에 처리된다. 별도 세션 중간 점검이나 상시 폴링은 필수가 아니다.

## 리뷰 범위와 문제 전달

동료는 **자기 파트가 사용하는 계약과 동작**을 확인한다. 전체 내부 구현을 다시 이해하거나 대신 작성하는 역할은 아니다.

- A ↔ B: 주문 이벤트·상품 전달·추천 호출과 응답, 평가 지표의 입력 형식.
- B ↔ C: 모델 manifest·학습·가중치 전달·설치.
- A ↔ C: 기동·환경변수·수명주기.
- 공통 JSON 계약·실행 환경: C가 조정하고 해당 소비자가 검토.

문제가 있으면 기존 PR의 리뷰에 기록해 작성자에게 전달한다. 이미 병합된 코드나 별도 후속 작업이면 담당 계정에 할당한 이슈에 기록하고 관련 PR에 링크한다. 소비자 검토 요청은 작성자가 아닌 해당 역할의 계정으로 보낸다. 그 역할이 아직 `미선점`이면 검토할 사람이 없으므로 그 PR은 병합하지 않고 기다린다. CODEOWNERS는 역할 소유 경로를 덮지 않아 자동 요청도 가지 않는다. PR 인계의 다음 담당 계정 칸에 `<역할> 미선점 · 선점 후 리뷰 요청`이라고 적고 독립 작업을 계속한다. 역할은 회의 직후 선점하므로 이 상태는 짧아야 한다. 외부 댓글·리뷰·이슈 작성은 해당 사용자가 위임한 GitHub 협업 범위에서 수행하며, 권한이 없으면 전달할 내용을 준비하고 미전달 상태를 명시한다.

```text
담당 역할 / 계정:
관련 PR / 검사한 head SHA:
심각도: 필수 수정 / 선택적 제안 / 사람 결정 필요
재현 입력·명령:
기대 동작 / 실제 동작 / 위반한 계약:
영향받는 파트와 막힌 작업:
```

- **필수 수정:** 버그·계약 위반·통합 실패. 담당 에이전트가 재현·수정·관련 검사를 하고 수정 SHA와 결과를 회신한다. 영향을 받는 에이전트는 연결 동작을 재확인한다. 기존 PR에서는 `Request changes`로 남기며 필수 수정이 남은 PR은 병합하지 않는다.
- **선택적 제안:** 취향이나 현재 완료 조건 밖의 개선. 병합을 막지 않는다.
- **사람 결정 필요:** 요구사항이나 계약 해석이 미정인 경우. 선택지·추천안·영향을 남기고 해당 부분만 보류한다. 결정 근거는 PR에 링크하고 지속되는 설계 결정은 [결정 기록](../design/decisions.md)에 반영한다.

수정자는 새 SHA·해결한 지적·검사 결과를 남기고 원래 소비자 검토자에게 명시적으로 재검토를 요청한다. 단순 push나 댓글만으로 재검토 요청이 전달되었다고 가정하지 않는다. 검토자는 확인한 SHA와 결과를 남기며, 필수 문제가 해결되면 이전 수정 요청을 승인 리뷰로 갱신한다. 작성자가 지적을 일방적으로 해결 처리하거나 미해결 상태를 숨기지 않는다.

PR 본문의 인계에는 `현재 상태 / 다음 행동 / 다음 담당 계정 / 관련 SHA·Issue`를 한 줄로 유지한다. 상태는 `구현 중 → 검토 대기 → 담당 수정 → 재검토 → 병합 가능 → 병합 완료`로 구분하고 결정이 필요하면 `사람 결정 대기`를 쓴다. 수정할 담당과 재확인할 담당을 구분하며 병합 실행의 기본 책임은 PR 작성자에게 있다. 리뷰어는 승인하면서 조건이 충족된 PR을 병합할 수도 있다. 역할 부재 시 전원에게 막연하게 넘기지 말고 다음 담당을 기록한 채 독립 작업을 진행한다.

담당자가 없다고 다른 역할의 구현을 넘겨받지 않는다. 합의된 현재 계약의 stub으로 자기 작업을 진행하고 실제 연결 검사가 남았음을 표시한다. 상대의 잘못된 동작에 맞춰 계약이나 stub을 몰래 바꾸지 않는다. 침묵은 승인이나 수정 완료가 아니다.

## 계약 변경과 통합

schema/함수/반환 타입/오류/모델 버전 변경은 생산자·소비자 영향, fixture와 동작 설명을 함께 검토한다. 새 계약의 의미는 사람이 결정하고, 합의된 계약의 구현·검증은 각 담당 에이전트가 맡는다. 추가 optional 필드도 strict v1에서 자동 호환이라고 가정하지 않는다.

기존 경로를 깨는 변경은 호환 전환이나 연관 PR의 순서를 먼저 정한다. 한 PR에 여러 소유자의 변경이 꼭 필요하면 각 담당이 자기 부분을 작성해 명시적으로 조정한다. C의 통합 조정은 다른 역할 구현을 대신 수정할 권한을 뜻하지 않는다.

## 병합과 복구

일반 병합에 사람의 클릭은 필요 없다. 담당 에이전트는 Ready인 PR에서 최신 `main`, 해당 head SHA의 검사, 필요한 소비자 검토·사람 결정, 의존 PR과 미해결 필수 수정의 부재를 확인한 뒤 병합하거나 예약한다. 부분 구현 PR은 이번 범위의 완료 조건과 남은 stub을 명시한다.

```text
gh pr merge <번호> --auto --merge --match-head-commit <확인한-head-SHA>
```

**예약 시점에 필요한 소비자 검토와 사람 결정이 이미 기록되어 있어야 한다.** 현재 GitHub 설정만으로 모든 종류의 검토·결정을 강제하지 못하므로 먼저 예약하고 나중에 검토받는 방식은 쓰지 않는다. 조건이 이미 충족되면 이 명령이 즉시 병합할 수 있다. 병합 결과는 실제 PR 상태로 확인한다.

`--match-head-commit`은 명령 실행 시 확인한 head와 실제 head가 같은지 확인한다. 예약 이후의 새 커밋까지 계속 고정하는 장치로 간주하지 않는다. 예약된 PR에 추가 push하기 전에는 예약을 취소하고 새 head의 검사·관련 재검토를 거쳐 다시 예약한다.

예약 후 필수 문제가 발견되면 권한 있는 에이전트가 `gh pr merge <번호> --disable-auto`로 취소하고 Draft로 돌린다. 권한이 없으면 작성자에게 즉시 상태 변경을 요청하며 미차단 상태를 기록한다. Draft 또는 수정 요청이 있는 동안 병합하지 않는다. 검토 후 동작이 바뀌면 기존 승인을 근거로 병합하지 않고 관련 재검토를 받는다.

**뒤처진 PR 갱신.** `main`이 앞서 나가 병합이 막히면(최신 브랜치 필수) 자동 병합 예약을 먼저 취소하고(`gh pr merge <번호> --disable-auto`), `gh pr update-branch <번호>`로 `main`을 병합 커밋으로 받는다. `--rebase`는 쓰지 않는다. `main`에서 온 변경만 더한 것이므로 받은 검토는 유지되고 재검토는 필요 없다. 새 head의 검사가 통과하면 그 SHA로 다시 예약한다. 세 역할의 선점 PR처럼 서로 충돌하지 않는 PR도, 하나가 병합될 때마다 나머지는 이렇게 갱신한다.

**의존 PR 쌓기.** 아직 병합되지 않은 PR 위에서 일해야 하면 그 PR 브랜치에서 분기하되 base는 `main`으로 두고 Draft로 연다. PR 템플릿의 Depends on에 의존 PR을 적는다. 의존 PR이 병합되면 위 방법으로 `main`을 받아 diff에 자기 변경만 남긴 뒤 Ready로 바꾼다. 의존 PR보다 먼저 병합하지 않는다. 기다리는 동안 다른 독립 작업은 `origin/main`에서 따로 분기해 진행한다.

의도가 명확하고 자기 담당 범위인 충돌은 담당 에이전트가 해결하고 재검사한다. 다른 소유자 구현의 충돌은 그 담당에게 전달하고, 어느 동작을 선택할지 미정이면 사람에게 올린다. `main` 직접 push, 보호 우회, force push, 공개 이력 rebase/amend, 자동 stash/pop·reset --hard·clean -fd로 알 수 없는 변경을 없애지 않는다.

통합 회귀는 원인 PR·재현·담당을 기록하고 담당자가 수정 또는 revert PR로 복구한다. 병합한 작업 브랜치는 재사용하지 않는다.

## CI와 저장소 설정

`Commerce checks`는 contracts/scaffold/docs/policy/business와 health smoke를 실행한다. 실제 서비스·모델·FL·보호 집계 완료를 보장하는 검사는 아니다. 담당자가 자기 소유 경로에 selfcheck를 추가하면 `business` 게이트를 통해 CI에 자동으로 연결되므로 C의 게이트 수정을 기다리지 않는다. 검사 실패는 먼저 담당자가 원인을 수정한다. 정책 자체를 바꿀 필요가 있을 때만 사람의 결정을 받으며 게이트를 우회하거나 통과 조건을 느슨하게 만들지 않는다.

2026-09-24 확인 기준: `main`은 최신 브랜치의 `scaffold` check를 필수로 요구하며 관리자에게도 보호가 적용된다. 저장소 자동 병합은 허용되어 있고 PR별 예약은 별도로 필요하다. 기존 승인 자동 취소와 미해결 대화 해소의 강제 설정은 꺼져 있다.

**GitHub이 강제하는 것은 두 가지다.** 하나는 필수 check다. 이름이 `scaffold`인 CI job으로, `gate scaffold`만이 아니라 모든 게이트(contracts·scaffold·docs·policy·business)와 smoke 실행을 돈다. 그래서 어느 게이트가 실패해도 병합이 막힌다. 다른 하나는 CODEOWNERS 경로의 소유자 승인이다. `require_code_owner_reviews`가 켜져 있어 그 경로를 바꾼 PR은 작성자가 아닌 소유자 한 명이 승인해야 병합된다. 필수 승인 수는 0이라 그 밖의 경로는 승인 없이 병합된다. 2026-09-24 PR #13이 소유자 승인 없이 병합을 거부당해 이 동작을 확인했다. 그보다 앞선 #9·#11은 CODEOWNERS 경로를 바꾸고도 승인 없이 병합됐는데, 당시 설정이나 권한이 지금과 달랐던 것으로 보인다. 이력만으로는 원인을 확인할 수 없으므로 선례로 삼지 않는다. 소비자 검토·사람 결정처럼 GitHub이 모르는 조건은 병합하는 에이전트가 확인한다.

설정은 값이 아니라 동작으로 확인한다. 보호 설정이나 CI를 바꾸는 PR은 이 절을 같은 PR에서 갱신하고, 강제된다고 적기 전에 승인 없는 테스트 PR이 실제로 막히는지 본다. 실제 작업 시 원격 설정이 바뀌었는지 확인한다.

CODEOWNERS는 경로 기반 리뷰 요청 장치다. 소비자별 리뷰 완료, 사람이 결정했는지 여부, 모든 버그·보안 위반은 자동 판정하지 않는다. 위의 병합 전 확인은 에이전트가 수행하는 운영 규칙이며 CI로 모두 강제되는 것으로 설명하지 않는다.

원자료·파생 거래/배정표·DB·가중치·인증 정보·로컬 보관 파일은 올리지 않는다. 공개 문서는 코드와 같은 PR/diff로 공유하며 별도 ZIP 동기화는 필요 없다.
