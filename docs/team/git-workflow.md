# Git 협업 규약

## 브랜치와 현재 상태

- `main`: 기존 연구 이력과 기존 기본 브랜치. 초기 코드가 자동 반영되지 않는다.
- `commerce/integration`: 공동 통합 기준. 동료 검토한 PR로 변경한다.
- `commerce/a/<작업>`, `commerce/b/<작업>`, `commerce/c/<작업>`: 담당별 짧은 작업 브랜치.
- 초기 뼈대는 [PR #3](https://github.com/CSID-DGU/2026-1-CECD1-3-JeonYeoGyeong-11/pull/3)에 있으며 초기 후속 작업은 이를 의존성으로 표시한다.

각자 별도 clone을 사용한다. 같은 사람이 여러 작업을 동시에 수행하면 별도 worktree/브랜치를 사용하고 하나의 index/작업 폴더를 동시에 수정하지 않는다.

## 시작·진행

1. `git status --short --branch`, `git remote -v`로 폴더·브랜치·기존 변경을 확인한다.
2. `git fetch origin` 후 최근 integration/의존 PR의 변경과 자기 경계에 영향을 주는 부분을 확인한다. 미병합 코드는 특정 head SHA의 diff 또는 별도 review checkout으로 확인한다.
3. 역할과 범위에 맞는 브랜치에서 구현한다. 다른 담당의 파일은 읽을 수 있지만 맡지 않은 구현을 임의로 바꾸지 않는다.
4. 검토 가능한 동작 단위로 관련 검사와 커밋을 남긴다. 명시 경로만 `git add`하고 staged diff를 확인한다. 작성자는 본인의 Git 정보로 설정한다.
5. 작업 브랜치를 push하고 integration 대상 Draft PR을 만든다. 현재 동작·미구현·검사 대상 SHA·재현 명령·의존 PR·받을 피드백을 기록한다. 로컬 커밋은 팀 공유 완료가 아니다.

원격을 확인할 수 없으면 미동기화 사실을 남기고 독립 작업은 계속한다. 최신 기준을 확인했다고 보고하지 않는다. 상대 브랜치를 자기 구현에 무작정 merge하거나 그 브랜치로 push하지 않는다.

## 계약 변경과 검토

공유 schema/함수/반환 타입/오류/모델 버전을 바꿀 때 생산자·소비자 영향, fixture, 동작 설명을 함께 검토한다. 계약 PR 후 구현 PR로 나누되, 기존 경로가 깨진다면 호환 전환이나 공동 변경으로 묶는다. 추가 optional 필드도 strict v1에서는 자동 호환이 아니다.

- A → B 이벤트·추천: A/B 검토.
- B → C 모델·학습·설치: B/C 검토.
- A → C 기동·수명: A/C 검토.
- JSON 계약·실행 환경: C가 조정하고 해당 소비자가 검토.

Ready 전 최신 integration을 반영하고 관련 검사·의존 PR·미해결 의견을 확인한다. 작성자 외 팀원의 검토가 필요하며 작성자 에이전트의 자체 검사를 동료 승인으로 세지 않는다. 기능 일부만 병합하는 PR은 그 부분의 완료 조건을 적고 미구현 전체 gate와 구분한다.

## 병합과 복구

병합은 실제 동료 검토와 요청 범위 확인 후 merge commit으로 수행한다. C가 조정하며 C 작성 변경은 해당 A/B 검토자가 병합할 수 있다. 작성자 단독 승인, integration 직접 push, force push, 공개 이력 rebase/amend로 검토를 우회하지 않는다.

충돌은 소유자와 의미를 확인해 해결하고 재검사한다. 자동 stash/pop·reset --hard·clean -fd로 모르는 변경을 없애지 않는다. 통합 회귀는 원인 PR과 재현을 남기고 수정/revert PR로 처리한다. 병합한 작업 브랜치는 계속 재사용하지 않는다.

## CI와 저장소 설정

초기 `Commerce checks` CI는 contracts/scaffold/health smoke를 실행한다. 서비스·모델·FL·보호 집계 완료를 보장하는 CI가 아니다.

브랜치 보호·required check·CODEOWNERS는 아직 설정하지 않았다. 팀원 계정과 권한을 확인한 뒤 최소 동료 승인 1건, 최신 변경 재검토, 미해결 의견 해소, 실제 존재하는 CI check를 기준으로 설정한다. 문서 규칙과 GitHub 강제 설정은 구분한다.

원자료·파생 거래/배정표·DB·가중치·인증 정보·로컬 보관 파일은 올리지 않는다. 공개 문서 변경도 코드와 같은 PR/diff로 공유하며 별도 ZIP 동기화는 필요 없다.
