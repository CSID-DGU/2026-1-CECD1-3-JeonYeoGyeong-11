# Git 협업 규약

## 누가 누구를 검토하는가

A/B/C는 **각자 다른 로컬 머신에서 동작하는 에이전트**이며 공유 수단은 이 저장소뿐이다. 그래서 "동료 검토"의 뜻을 아래로 고정한다.

| 단계 | 주체 | 인정 범위 |
| --- | --- | --- |
| 계약 검토 | **작성자가 아닌 다른 역할의 에이전트** | 소비자 역할을 우선한다(A 변경은 B·C 중 소비자, B 변경은 A·C, C 변경은 A·B). 계약·호출 예제·경계 위반을 본다 |
| 병합 승인 | **사람(운영자)** | 실제 병합은 사람이 수행한다. 에이전트는 병합하지 않는다 |
| 자동 검사 | 게이트·CI | 위 둘을 대체하지 않는다 |

작성자 에이전트의 자체 검사는 검토도 승인도 아니다. 다른 역할 에이전트의 검토 의견은 PR 코멘트로 남겨 사람이 읽을 수 있게 한다. 검토자를 찾지 못하면 Draft로 두고 무엇이 막혔는지 PR에 적는다. 승인이 없다는 이유로 자기 PR을 병합하지 않는다.

각 에이전트는 **구별되는 Git 작성자 정보**를 사용한다(예: `A (agent) <계정>`). 세 역할이 같은 identity로 커밋하면 누가 무엇을 바꿨는지 이력에서 복원할 수 없다.

## 브랜치와 현재 상태

- `main`: **공동 통합 기준이자 기본 브랜치.** 검토를 거친 PR로만 변경한다. 기존 Graph-FL 연구는 이력에만 남아 있다.
- `commerce/a/<작업>`, `commerce/b/<작업>`, `commerce/c/<작업>`: 담당별 짧은 작업 브랜치. PR의 base는 항상 `main`이다.
- `commerce/integration`은 `main`과 같은 내용의 중복 브랜치여서 은퇴했다. 여기서 분기하거나 여기로 PR을 보내지 않는다.

각 에이전트는 자기 머신의 별도 clone을 사용한다. 한 에이전트가 여러 작업을 동시에 수행하면 별도 worktree/브랜치를 사용하고 하나의 index/작업 폴더를 동시에 수정하지 않는다.

## 시작·진행

1. `git status --short --branch`, `git remote -v`로 폴더·브랜치·기존 변경을 확인한다.
2. `git fetch origin` 후 최근 `main`/의존 PR의 변경과 자기 경계에 영향을 주는 부분을 확인한다. 미병합 코드는 특정 head SHA의 diff 또는 별도 review checkout으로 확인한다.
3. 역할과 범위에 맞는 브랜치에서 구현한다. 다른 담당의 파일은 읽을 수 있지만 맡지 않은 구현을 임의로 바꾸지 않는다.
4. 검토 가능한 동작 단위로 관련 검사와 커밋을 남긴다. 명시 경로만 `git add`하고 staged diff를 확인한다. 작성자는 본인의 Git 정보로 설정한다.
5. 작업 브랜치를 push하고 `main` 대상 Draft PR을 만든다. 현재 동작·미구현·검사 대상 SHA·재현 명령·의존 PR·받을 피드백을 기록한다. 로컬 커밋은 팀 공유 완료가 아니다.

원격을 확인할 수 없으면 미동기화 사실을 남기고 독립 작업은 계속한다. 최신 기준을 확인했다고 보고하지 않는다. 상대 브랜치를 자기 구현에 무작정 merge하거나 그 브랜치로 push하지 않는다.

## 계약 변경과 검토

공유 schema/함수/반환 타입/오류/모델 버전을 바꿀 때 생산자·소비자 영향, fixture, 동작 설명을 함께 검토한다. 계약 PR 후 구현 PR로 나누되, 기존 경로가 깨진다면 호환 전환이나 공동 변경으로 묶는다. 추가 optional 필드도 strict v1에서는 자동 호환이 아니다.

- A → B 이벤트·추천: A/B 검토.
- B → C 모델·학습·설치: B/C 검토.
- A → C 기동·수명: A/C 검토.
- JSON 계약·실행 환경: C가 조정하고 해당 소비자가 검토.

Ready 전 최신 `main`을 반영하고 관련 검사·의존 PR·미해결 의견을 확인한다. 위 §누가 누구를 검토하는가에 따라 다른 역할 에이전트의 검토를 받고 사람이 병합한다. 작성자 에이전트의 자체 검사를 동료 승인으로 세지 않는다. 기능 일부만 병합하는 PR은 그 부분의 완료 조건을 적고 미구현 전체 gate와 구분한다.

## 병합과 복구

병합은 다른 역할 에이전트의 검토와 요청 범위 확인을 거친 뒤 **사람이** merge commit으로 수행한다. C가 조정하지만 에이전트는 어느 역할이든 스스로 병합하지 않는다. 작성자 단독 승인, `main` 직접 push, force push, 공개 이력 rebase/amend로 검토를 우회하지 않는다.

충돌은 소유자와 의미를 확인해 해결하고 재검사한다. 자동 stash/pop·reset --hard·clean -fd로 모르는 변경을 없애지 않는다. 통합 회귀는 원인 PR과 재현을 남기고 수정/revert PR로 처리한다. 병합한 작업 브랜치는 계속 재사용하지 않는다.

## CI와 저장소 설정

초기 `Commerce checks` CI는 contracts/scaffold/docs/health smoke를 실행한다. 서비스·모델·FL·보호 집계 완료를 보장하는 CI가 아니다.

브랜치 보호·required check·CODEOWNERS는 아직 설정하지 않았다. 에이전트 계정과 권한을 확인한 뒤 최소 검토 1건, 최신 변경 재검토, 미해결 의견 해소, 실제 존재하는 CI check를 기준으로 설정한다. 문서 규칙과 GitHub 강제 설정은 구분한다.

원자료·파생 거래/배정표·DB·가중치·인증 정보·로컬 보관 파일은 올리지 않는다. 공개 문서 변경도 코드와 같은 PR/diff로 공유하며 별도 ZIP 동기화는 필요 없다.
