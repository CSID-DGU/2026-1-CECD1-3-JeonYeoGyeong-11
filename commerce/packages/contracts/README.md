# 계약 검증

[스키마](schemas/)와 [정상·오류 예제](fixtures/)를 검증합니다. 전체 계약 목록과 게이트 상태는 [계약 문서](../../../docs/contracts.md)를 참고합니다.

프로젝트 루트에서 실행합니다.

```text
python -m commerce.tools.gate contracts
```

표준 라이브러리와 `jsonschema`를 사용합니다. 성공은 종료 코드 0과 마지막 줄의 `CONTRACTS OK: schemas=<n> fixtures=<n> failures=0`으로 확인합니다.

JSON Schema 2020-12가 필드·타입 기준이며 검증기의 의미 검사도 적용합니다. 미지 필드를 거부하므로 optional 필드 추가도 자동 호환으로 취급하지 않습니다. 변경 시 생산자·소비자, 스키마·예제·공개 동작 설명을 함께 맞춥니다.

정상 예제는 `fixtures/<계약>/valid`, 오류 예제는 `invalid`에 둡니다. 예제의 ID는 원자료의 실제 값을 쓰지 않습니다. `dh-p-…`, `ic-o-…`처럼 출처 형식을 흉내 낼 때는 실제 범위 밖의 값을 씁니다(예: `ic-p-990001`). 이미 공개한 기준 roster의 점포 ID는 예외입니다. 오류 예제와 이름이 같은 `.reason.txt` 첫 줄은 기대 오류 코드이며 다음 줄은 설명입니다.

`round_submission.v1`은 생성 합성 데이터의 평문 연결 검사 전용입니다. 중첩 `delta_manifest` 사본은 원본 스키마와 일치하는지 검사합니다. `model_release.v1`은 버전·manifest/weights 해시·길이를 기술합니다. 보호 프로토콜 메시지는 구현 선정 뒤 별도 계약으로 추가할 예정입니다.

`purchase_event_id`는 규칙대로 계산한 실제 값이며 검증기가 규칙과 대조합니다. 계산은 `ids.py`의 함수를 쓰고 따로 구현하지 않습니다. 그 밖의 예제 해시는 형태 예시입니다. 실제 해시·배열 내용·인증·주문 복구·모델 학습·보호 집계는 각 구현 게이트에서 확인해야 합니다. 과거 확장용 허용값도 남아 있어 스키마 통과만으로 서비스 지원을 주장하지 않습니다.

로컬 Python 인터페이스는 `ports.py`, 반환 객체는 `types.py`, 오류는 `errors.py`, 두 역할이 같이 계산하는 식별자·해시는 `ids.py`에 있다. 호출 경로·소유권·다음 구현은 [개발 안내](../../../docs/development.md)를 따른다.
