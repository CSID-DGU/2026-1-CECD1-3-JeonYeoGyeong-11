# Repository work guide

**This is the shared entry point for every coding agent.** A/B/C may use different tools on separate machines. Vendor-specific instruction files must stay short and point here; do not duplicate project rules in them.

The gates in `commerce/tools/` and CI enforce a subset of these rules. Review routing, ownership and human decisions also require the workflow below; a green CI result does not prove those steps happened. GitHub enforces one thing: the required CI job named `scaffold`, which runs every gate plus the smoke run, must pass on an up-to-date branch. It enforces no approval, even on CODEOWNERS paths, so the merging agent checks approvals itself.

- Read this file, then `docs/team/start.md` and only your own A/B/C card. If line 2 of your card says `미선점`, open the one-line claim PR in `docs/team/working-agreement.md` §1 before any work PR, after the user confirms the GitHub account is theirs. Follow the scoped reading guide there; do not preload all of `docs/`. Inspect the relevant package code and contracts before implementing a bounded task. `docs/README.md` is a lookup index, not required reading in full. No private document bundle is required.
- At session start, check your PR feedback, assigned issues, requested reviews and open PRs affecting your role, then inspect only new relevant diffs. Use the commands in `docs/team/git-workflow.md`; there is no background review watcher. Prioritize work that blocks peers without waiting for every peer to be online.
- Use `docs/team/working-agreement.md` §1 for ownership and §3–4 when touching runtime or gates. Read the applicable steps in `docs/team/git-workflow.md` before Git/review actions. Preserve unrelated changes and history. Cross-owner implementation needs explicit user assignment; coordinate shared contracts with consumers.
- Use `commerce.packages.*` imports. Local APIs/types/errors live in `commerce/packages/contracts/ports.py`, `types.py`, and `errors.py`; identifiers and hashes that two roles must compute identically live in `ids.py`. Wire fields/types are defined by JSON schemas and the validator; behavior is specified in `docs/design/interfaces.md` and `model.md`. Resolve conflicts together instead of silently choosing a different contract. Old document names and rule IDs such as `R6` or `§8` in schema descriptions and code comments are historical. docs/contracts.md maps the old file names to interfaces.md and model.md; the old rule numbers have no table, so find the rule by topic there instead of searching for the old files. Abbreviations in the role cards are defined in docs/team/start.md §5.
- Inspect actual code and gate output. Current service/model/FL business functions are stubs; do not turn FeatureNotImplemented or NOT_IMPLEMENTED into false success.
- Keep raw transactions, customer data, local features, individual model updates, DBs, weights and secrets out of Git and central logs. Real-data-derived FL requires the protected path. Synthetic plaintext is only for generated synthetic input.
- Keep shared base, FL training copies and personalized serving copies separate. Personalization is query_proj/scorer only; never export it for FL. Train text_only and text_relation independently.
- Run `python -m commerce.tools.gate contracts` for contract changes, `python -m commerce.tools.gate scaffold` for interface/lifecycle changes, and `python -m commerce.tools.gate docs` when you touch docs, env vars, gate names or the documented imports. Run your own business gate (`python -m commerce.tools.gate a1|b1|b2|c1`); it is pre-wired to a `selfcheck.py` in your path (docs/contracts.md), so add that file instead of editing `gate.py`. CI runs every business gate through `gate business`, which allows NOT_IMPLEMENTED but not failures. Reserve wider integration checks for a concrete integration risk. `python` here means the project venv interpreter (`.venv\Scripts\python` on Windows, `.venv/bin/python` elsewhere); a bare `python` on PATH may belong to another project and lack the locked dependencies.
- Work in a scoped branch and your own checkout. Stage explicit paths, inspect staged files, and follow the user's authorization for commit/push. Agents may merge eligible PRs or enable auto-merge under `docs/team/git-workflow.md`; no direct main push, force push or protection bypass. Internal changes need checks; cross-role behavior needs affected-consumer review; unresolved product, contract, model or security decisions need a recorded human decision first. Your own tests do not count as peer review.
- Report bugs in another role's code on its PR or an assigned issue with reproduction, expected/actual behavior, affected contract and tested SHA. The owning agent fixes them; do not take over another role's implementation because its owner is absent. Review the consumed behavior rather than relearning the entire implementation. Blocking findings keep the affected PR unmerged until fixed and rechecked; optional suggestions do not block.
- Move a PR from Draft to Ready when it is ready for review, not after review. Re-request consumer review after fixes, and keep the next action, responsible account and checked SHA in the PR handoff. Cancel auto-merge before adding commits to a queued PR; recheck the new head before re-enabling it.
- Continue independent work using contract-compatible test doubles when peers are unavailable. Do not treat silence as agreement. Open decisions are tracked in `docs/design/open-questions.md`.
- Report implemented behavior, exact checks, remaining stubs, affected interfaces and the next small task. Read relevant diffs on continuation; avoid repeatedly summarizing all documents.
- `.team/`, `tmp/`, old archives and local data are historical/private material, not prerequisites or current implementation authority. Do not publish them through force-add.
